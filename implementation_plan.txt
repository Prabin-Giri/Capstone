# Plagiarism Detection Plan (Local, Multi-Language, Integratable)

## Goal

Build a standalone plagiarism detector that:

* works locally (no APIs),
* supports multi-file submissions + multiple languages,
* produces **scores + evidence** (matched code regions),
* runs independently of grading (can be async later),
* is easy to integrate once DB/UI exist.

---

## Phase 1 — Build the MVP Pipeline (Works end-to-end)

### Step 1: Load submissions (Loader)

* Walk each submission folder.
* Collect only source files by extension:

  * `.py .java .js .jsx .ts .tsx .php .html` (and any others needed)
* Ignore junk folders:

  * `node_modules, venv, .git, dist, build, __pycache__`
* Output a structure like:

  * `Submission { id, files: [ {path, text} ] }`

Deliverable: `loader` module + unit test with a fake folder.

---

### Step 2: Tokenize + normalize (Normalizer)

Start with a regex-based tokenizer (fast MVP).
For each file:

* Remove comments (best-effort per language).
* Split into tokens (identifiers, keywords, numbers, strings, operators).
* Normalize tokens to reduce false positives:

  * identifiers → `ID`
  * numbers → `NUM`
  * strings → `STR`
  * optionally keep keywords/operators as-is
* Keep mapping from token index → original (file, line range) for evidence later.

Deliverable: `normalize` module that outputs:

* `tokens: [normalized_token]`
* `token_locations: [ {file, start_line, end_line} ]`

(Upgrade later: swap tokenizer with Tree-sitter without changing fingerprint logic.)

---

### Step 3: Fingerprinting (Winnowing)

For each submission’s combined token stream:

* Concatenate tokens from all files in deterministic order (sorted by relative path).
* Insert a marker token between files (e.g., `FILE_BOUNDARY`) to prevent weird cross-file matches.
* Build k-grams of tokens (suggest starting values):

  * `k = 25` tokens
* Hash each k-gram.
* Apply **winnowing** with window size:

  * `w = 4`
* Store:

  * fingerprint set (hashes)
  * fingerprint occurrences → token positions (for evidence)

Deliverable: `fingerprint` module:

* `fingerprints: Set[int]`
* `fp_hits: Dict[hash -> List[token_index]]`

---

### Step 4: Candidate matching (MVP: pairwise, then optimize)

MVP (good enough early):

* For all pairs of submissions in the assignment:

  * compute similarity using fingerprints

Later optimization (recommended):

* Build an inverted index:

  * `hash -> list of submission_ids`
* For each submission, candidates are only ones that share enough hashes.

Deliverable MVP: `compare` module that returns pair scores.

---

### Step 5: Similarity scoring

For each pair (A, B):

* `intersection = |Fa ∩ Fb|`
* `jaccard = intersection / |Fa ∪ Fb|`
* `containment = intersection / min(|Fa|, |Fb|)` (very useful when one is a superset)

Store both scores.

Deliverable: pair scoring + thresholding logic:

* Keep pairs where containment or jaccard exceeds a threshold (start low, tune later).

---

### Step 6: Evidence generation (MVP then improved)

MVP evidence:

* For shared fingerprint hashes, list:

  * which files/lines in A and B contain those fingerprints (via token index mapping)
* Output a list of “hits” that the instructor can inspect.

Improved evidence (next upgrade):

* Merge nearby hits into **contiguous regions**:

  * sort hits by token index,
  * group into runs,
  * map runs back to file + line ranges,
  * show small snippets.

Deliverable: `evidence` module producing:

* `matched_regions: [{fileA, linesA, fileB, linesB, snippetA, snippetB}]`

---

### Step 7: Reporting (JSON + optional CSV)

Create `report.json` with:

* assignment info
* summary:

  * total submissions
  * total suspicious pairs
* top pairs:

  * `subA, subB, jaccard, containment, matched_regions_count`
* per-submission view (optional):

  * “top 5 most similar others”

Deliverable: `report` module + CLI output.

## Phase 3 — Upgrades (After MVP Works)

### Upgrade A: Tree-sitter tokenization

Replace regex tokenizer with Tree-sitter for:

* better comment handling
* accurate token stream
* reliable location mapping

Do this behind a `LanguagePlugin` interface.

### Upgrade B: Candidate indexing (scaling)

Implement inverted index per assignment to avoid O(n²).

### Upgrade C: Starter code suppression

Allow instructor to provide starter/template files.
Fingerprint starter code and subtract those hashes from all submissions before comparisons.

### Upgrade D: Downweight common fingerprints

If many students share the same fingerprint (boilerplate), downweight it (IDF-like heuristic).

## Phase 3 — Complexity & Risk Analysis

### Upgrade A: Tree-sitter tokenization
* Complexity: ⭐⭐⭐ Medium-High
* Time: ~1-2 hours
* Risk: MEDIUM — Tree-sitter requires installing language-specific grammar
  packages (e.g., tree-sitter-python, tree-sitter-java). These are native
  C libraries compiled via pip, which can fail on some systems. If it works,
  it's a clean swap inside normalizer.py. If the install fails, we're stuck
  debugging C compiler issues.
* What could break: Nothing in the existing code — we'd add a new normalizer
  behind a flag. Old regex normalizer stays as fallback.

### Upgrade B: Candidate indexing
* Complexity: ⭐⭐ Medium
* Time: ~30-45 min
* Risk: LOW — Pure Python logic change inside compare.py. Build an inverted
  index (hash → list of submissions), then only compare pairs that share
  at least N hashes. No new dependencies. Only matters when you have 50+
  submissions; for small classes (<30) the current pairwise approach is fine.
* What could break: Nothing. It's an optimization, not a behavior change.

### Upgrade C: Starter code suppression
* Complexity: ⭐ Easy
* Time: ~20-30 min
* Risk: LOW — Add a --starter flag to CLI that points to the template files.
  Fingerprint those files, then subtract their hashes from all submissions
  before comparison. Very clean change.
* What could break: Nothing. Pure addition.

### Upgrade D: Downweight common fingerprints (IDF)
* Complexity: ⭐⭐ Medium
* Time: ~30-45 min
* Risk: LOW-MEDIUM — Instead of treating all shared fingerprints equally,
  give less weight to fingerprints that appear in many submissions. This
  changes the scoring formula in compare.py. Risk is that tuning the
  weights wrong could cause false negatives (missing real plagiarism).
  Needs careful threshold tuning.
* What could break: Scoring accuracy if weights are poorly tuned.

### Summary table:

| Upgrade | Time | Risk | Recommendation |
|---------|------|------|----------------|
| A. Tree-sitter | 1-2 hrs | Medium | Skip unless regex causes problems |
| B. Candidate index | 30-45 min | Low | Skip unless class has 50+ students |
| C. Starter code | 20-30 min | Low | DO THIS if professors give starter code |
| D. IDF weighting | 30-45 min | Low-Med | Nice-to-have, not urgent |

⚠️ Known Limitations (things that might not work perfectly)
1. Code restructuring won't be caught
If a student copies code but reorders the functions (e.g., moves 

main()
 to the top), the fingerprints change because winnowing is order-dependent. This is a fundamental limitation of the algorithm — only Tree-sitter (Phase 3 Upgrade A) would partially fix this.

2. Adding dead code defeats it
If someone copies your code and then adds 50 lines of junk/unused functions to dilute it, the Jaccard score drops significantly. The containment score helps here, but a clever student could still game it.

3. Only tested with Python files
While the normalizer supports JS/Java/C++, all our test fixtures are Python. Comment removal for other languages uses regex which is best-effort — for example, a string like "http://example.com" could be mistakenly treated as a // comment in JS/Java.

4. No cross-submission-attempt comparison
If a student submits multiple times, the tool treats each submission folder independently. It doesn't compare Attempt 1 vs Attempt 2.

5. Scale concern for large classes
With 100+ students, that's ~5,000 pairs to compare. Python will handle it, but it'll take a few seconds. For 500+ students it could be slow (Phase 3 Upgrade B — candidate indexing — would fix this).

6. No integration with your web app yet
Right now it's a CLI tool only. A faculty member can't click "Check Plagiarism" in the UI and have it use this engine. That's the integration work we skipped (Phase 2 Step 9).

Bottom Line
For your capstone project, this tool is production-ready for the core use case: detecting copied code with variable renames, partial copying, and boilerplate suppression. The limitations above are edge cases that would require significantly more work and are beyond what most plagiarism tools handle anyway (even MOSS has similar limitations).
